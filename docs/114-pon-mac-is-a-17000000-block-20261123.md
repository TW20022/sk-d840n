# The PON MAC is a 0x17000000 block, not part of the NPPT window

Date: 2026-11-23. Board: SK-D840N, ImmortalWrt 25.12.1 / Linux 6.18.60 (cnjn target).

## What was wrong

Every PON register the driver has written since `docs/107` resolved against
`eth->base`, the **NPPT** window at `0x19000000`:

```c
zx_pon_hw = eth->base;                       /* nppt */
zx_xmac_w(0x16636, ...);                     /* -> 0x19_058D8 */
```

The PON MAC is a separate 16 MiB block at `0x17000000`. Nothing the driver
wrote ever reached it, which is why every hardware-side claim in `docs/107`
and `docs/113` was in fact a software-side claim:

| observation | real cause |
| --- | --- |
| `pon_hw ... mapped=1 tx=<grows>` | `tx` is `zx_ploam_tx_n`, a software counter |
| `tx_kick=00000001` once | the nppt offset `0x59908` aliases another block |
| `pon_state` reaches O5, `omci error=0` | fully software; the injected frames come from genl |
| GEM table `done` bit never sets | `0x16206` in the nppt window is not the table engine |

The first hard evidence came from a register dump through the nppt mapping:
of `0x16000..0x17000` only 14 words were non-zero, all inside
`0x16000..0x16048`; everything from `0x16100` up read back zero. The vendor
does `Hal_ReadXmacReg(0x16206)` expecting a done bit and `Hal_ReadXmacReg(0x1650f)`
expecting the current T-CONT word, so those registers are readable on the real
block - they simply are not at that address.

## The decode, from the vendor modules

`oem_rootfs.tar.gz` carries the whole vendor stack:

* `zte_xgpon.ko` defines the accessors that the PON code calls:

```
Hal_ReadXmacReg:   bl fpga_read_reg        ; (reg, &value)
Hal_WriteXmacReg:  bl fpga_write_reg       ; (reg, value)
```

* `zx_ponreg_133.ko` defines `fpga_read_reg_one`:

```
cmp  w0, #0x3fffff            ; reg > 0x3fffff -> return 0
b.hi 350
ubfiz x0, x0, #2, #32         ; reg * 4
ldr  x1, [base]               ; base = pon_base
ldr  w0, [x1, x0]             ; word read at pon_base + reg * 4
```

So the vendor's register numbers are **word indices**, and `base` is
`pon_base`, which `np_133.ko` keeps in its own `.bss` at offset 0x10.

* The stock device tree (`decompiled/sk-d840n-stock.dts`) says what `pon_base` is:

```
pon@17000000 {
        compatible = "zte,zx279133-pon";
        reg = <0x00 0x17000000 0x00 0x1000000   /* PON MAC */
               0x00 0x10e00000 0x00 0x1000      /* intc */
               0x00 0x10e10000 0x00 0x10000     /* topcrm */
               0x00 0x10e20000 0x00 0x1000      /* pinctrl */
               0x00 0x14f11000 0x00 0x1000>;    /* pwm */
        interrupt-parent = ...;
};
```

`0x17000000 + 0x16636 * 4 = 0x170_598D8`. The NPPT node is a *different*
block (`0x19000000`), so the two were never the same address space.

## Why no byte-offset variant

An earlier attempt read the same numbers as byte offsets (`base + 0x1650f`)
and the board wedged with no serial output at all. `0x19000000` maps a 16 MiB
resource but decodes sparsely: `nppt + 0x1611d` is a hole, and a read of a hole
stalls the AXI bus. Word indexing through the nppt window never faults, it just
returns zero - which is exactly what the dump showed.

## Why the block cannot simply be mapped yet

Mapping `0x17000000` and running `zx_pon_hw_bringup()` on it hangs the board in
the same way (no serial, no network, only a power cycle recovers). The PON block
is clock-gated, and nothing on this tree enables its gates. The mainline clock
driver already knows them:

```
ZX279133_TOPCRM_PON_GATE_CTRL 0x48   (topcrm at 0x10e10000)
  bit 0  pon_idm_aclk
  bit 1  pon_tm_aclk
  bit 2  pon_pclk
  bit 7  pon_smac_wclk
  bit 12 pon_mac_wclk
```

`drivers/clk/clk-zx279133.c` registers these five gates with
`CLK_IGNORE_UNUSED`, i.e. it keeps whatever the firmware left behind and never
enables them itself. With the gates off, any access to the PON block stalls.

## Order of work from here

1. Enable the five PON gates in topcrm (`0x10e10000 + 0x48`) from the PON
   attach path, before any register access. Topcrm itself answers normally.
2. Do **not** touch `0x17000000` during probe. Map it, then expose a small
   register window through sysfs and poke it from userspace instead.
3. Arm `/dev/watchdog0` (the `zx279133_wdt` driver, key `0x12340000`, base
   `0x14f09000`) around every risky access so a bus stall costs a 15 s reboot
   rather than a physical power cycle.
4. Re-run the bench in `docs/113`: with the real block, `0x1650f` must read back
   the T-CONT word and `0x16206` must raise the GEM table done bit.

Recovery image used after the hang: the same source with the mapping left at
`eth->base`, flashed from U-Boot over TFTP (`pon_revive/uboot_kernel_recover.py`).
