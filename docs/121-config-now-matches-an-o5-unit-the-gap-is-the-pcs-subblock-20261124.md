# 121 — 配置已与 O5 活机逐位对齐，缺口收窄到「SerDes → XMAC1」之间的 PCS 子块

日期：2026-11-24 19:20 起（无纤可动，全程只读 + RAM 热写，未刷机、未改 flash）

## 0. 这一轮做了什么

用户不方便把光纤从 HX5 移到 SK，于是把「插纤前能做的」全部做完：
把本板在场的每个 PON 寄存器，逐个和 HX5-9saLite 在 **O5 在线**（`hx5_o5_regdump_20261124_081416.txt`、
`hx5_route_regs_20261124_105515.txt`）上的值对齐，直到**没有任何一处可识别的配置差异**为止。

结论先写：**XMAC1 侧已经无可调项**。剩下的差异只有一处——本板 PON 窗口 `+0xB0000`
那一段子块整段读 0、写不进，而 HX5 上 `0x170B0010 = 0x07D0000C`。

## 1. 本板搬到「厂商 XG bring-up 后」的状态（RAM only）

```
echo force > /sys/class/net/eth0/pon_arm      # 级联：map + zx_pon_hw_bringup()（XG 版）
```

读回（`pon_probe`）：

| 寄存器 | 本板（force 后） | HX5 @ O5 | 判定 |
|---|---|---|---|
| 0x16644 MAC mode | **0x00001b01** | 0x1B01 | ✓ |
| 0x1688e preamble | 0x00000020 | 0x20 | ✓ |
| 0x1611d repeat | 0x000fffff | 0xFFFFF | ✓ |
| 0x16100 | 0x0000063a | 0x63B | 差 bit0（下行使能，O5 才置） |
| 0x16600 | 0x00000015 | 0x15 | ✓ |
| 0x16635 | 0x00000001 | 0x1 | ✓ |
| 0x16000 | 0x00000000 | 0x0 | ✓（自清握手） |
| 0x1610b | 0x00000000 | 0x0 | ✓ |
| 0x16206 GEM 空闲 | 0x00000001 | 0x1 | ✓（engine ready） |

把 `0x16100 bit0` 置上后读回 **0x63b**，与 HX5 逐位相同（`m 16100 0 1`）。
⇒ 下行使能也不是原因（docs/118 已排除过一次，这次在正确 MAC 模式下复核仍排除）。

## 2. SerDes 49 字：与 HX5 @ O5 逐字相同

本板用 `rdreg 0x16000000..0x160000c0`（真实 SerDes 块，**不是** `pon_reg` 索引——
`pon_reg` 的 `0x160xx` 落在 PON 窗口 `+0x58000` 的 XMAC1 寄存器组，两者别混），
与 `phy-zx279133-pon-serdes.c` 的 `zx279133_pon_serdes_xgpon_nsyn_profile[]` 及 HX5 对比：

```
w00..w15  本板 == 表 == HX5
w16       本板 0x05a8d100   HX5 0x05a85100   ← 唯一差异
w17..w31  全同（含 w21 = 0x101，即 ACTIVATE1_EN 置位）
w40 0x55555555 / w48 0 / w94 0 / w0e8 0 / w0ec 0 全同
```

`w16` 的差是 **bit15**。`zx279133_pon_serdes_write_profile()` 里
`ACTIVATE0(0x40) |= ACTIVATE0_EN(0x8000)`，即 bit15 是「配置装入/激活」选通位。
本板的 U-Boot 把它留成 1（激活完成不回零），HX5 上是 0。热写 `0x05a85100` 后
读回成功、`0x16105` 与 `rx` 不变；已恢复 `0x05a8d100`。
⇒ 选通位状态不是原因，但它说明**本板 U-Boot 的 SerDes 收尾与 HX5 不完全一样**。

## 3. 线速实测：OLT 发的是 XG-PON 9.95328 Gb/s（决定性）

`0x160000e8` 是恢复时钟域的 32 位字计数器。同一条 SSH 会话内两次读，间隔 10 s：

```
v1 = 0x8fcd0afa   v2 = 0x49673721   （32 位回绕）
增量 = 4294967296 - 0x8fcd0afa + 0x49673721 = 3113380391
⇒ 3.1134e8 字/s × 32 bit = 9.963 Gb/s
```

与 **XG-PON 下行 9.95328 Gb/s ÷ 32 = 3.1104e8 字/s** 只差 0.1%（读数间隔略超 10 s），
与 XGS-PON 10.3125 Gb/s（3.2227e8 字/s）差 3.5%。
⇒ **OLT 侧是 XG-PON，不是 XGS-PON**；本板的 `fi_Configure_Pon_Mode(3)`（0x6 低 4 = 3、
0x1688e = 0x20、0x1611d = 0xfffff、0x16644 = 0x1b01）方向正确，不必再试 XGS 全序列。
⇒ 同时说明 SerDes 的 CDR 锁在**真实**线路速率上，RX 模拟通道没有问题。

## 4. pon_route 与厂商 en=0 三件套：已对齐，仍无效

`ponserdes_to_xmac1_en_set(en)`（np_133.ko @0x1c4）完整语义：

```
if (en==1 || en==0) NPPT+0x19c bit0 = en        // greg_sdet_share_clk_cfg
*(pon_base + 0x80) = (en != 1)                  // 物理 0x17000080 = pon_reg 索引 0x20
NPPT[0x2438] bit2  = (en != 1)
```

实测：

| 状态 | 0x17000080 | 0x19002438 | NPPT+0x19c |
|---|---|---|---|
| 本板刚开机 | **0** | 0x7 | 0x1 |
| HX5 @ O5 | **1** | 0x7 | 未采 |
| 本板按 en=0 全量重放 | 1（可保持） | 0x7 | 0 |

三种组合下 `0x16105` 恒 = `0x10`、`0x16148` 恒 0、SDET FIFO（0x19002440/44）恒 0。
⇒ 路由方向第二次排除（这次是在 0x16644 = 0x1b01 的正确前提下）。

## 5. PCS 视角：PCS 活着、在判同步、但每个块都判错

```
xpcs lane 0 devad 0x3 reg 0x01 = 0x00c2     block_lock(bit0)=0, hi_ber(bit1)=1
xpcs lane 0 devad 0x3 reg 0x02 = 0x7996
xpcs lane 0 devad 0x3 reg 0x00 = 0x0440
xpcs lane 0 devad 0x1 reg 0x01/0x08/0x09 = 0x0000
xpcs lane 0 devad 0x4 reg 0x01/0x18/0x19 = 0x0000
xpcs lane 0 devad 0x5 reg 0x01 = 0x0000
```

`hi_ber = 1` 且 `block_lock = 0`、而不是「PCS 完全不动」，说明 PCS 有输入时钟、
正在对 64b/66b 同步头做判定，但**收到的每个块同步头都非法**。
这与「帧一个都不来、错误计数也为 0」的组合相符：数据在 PCS 之前就不是合法的 66b 流。

## 6. 唯一剩下的硬件差异：PON 窗口 +0xB0000 整段未活

> **本节结论已在 docs/122 被推翻（2026-11-24 20:15）。**
> HX5 上 `0x170B0000–0x170B007C` 是 **32 个内容完全相同的字**（全 `0x07D0000C`），
> 相邻的 `0x17090000/0x170A0000/0x170C0000…0x170F0000` 两块板都是 0；厂商 `zte_xgpon.ko`
> 的 XMAC 写索引里没有 `0x2C0xx`；本板写它被丢弃。这是一个**地址别名返回的常量**，
> 不是"未上时钟的寄存器块"，`0x07D0000C` 也不是子块时钟使能位域。
> TOPCRM 与内核时钟树都已查过，没有任何 PON 时钟被门控关闭。下面的内容保留作过程记录。

```
本板                                       HX5 @ O5
0x17090000 = 0x00000000                    未采
0x170A0000 = 0x00000000                    未采
0x170B0000 = 0x00000000                    未采
0x170B0010 = 0x00000000  (写 0x7D00000C 读回 0)  0x170B0010 = 0x07D0000C
0x170B0060 = 0x00000000                    0x170B0060 = 0x07D0000C
0x170C0000..0x170F0000 = 0x00000000        未采
```

对照：`0x17000000 = 0x27913200`（die ID）、`0x17040000 = 1`、`0x17050000 = 1`、
`0x17058414 = 0x10`（XMAC1 寄存器组）都正常。
⇒ 本板 **0x17090000–0x170FFFFF 这一段整段读 0**，写也丢；HX5 同地址返回有效配置字。
一块寄存器整段读 0 + 写不进，是**未上时钟/未解除门控**的典型表现，不是配置值问题。

`0x170B0010` 的值 `0x07D0000C` 位域为 {2,3,20,22,23,24,25,26}，形状像一组子块时钟使能。
np_133.ko 里**没有**任何 `Hal_WriteXmacReg` 访问索引 0x2C004
（`tools/xmac_map.py np_133.ko 0x2c004 0x2c0004 0x2c0018` 全为 none），
说明这段不是 PON MAC 驱动配的，而是**引导器 / TOPCRM 侧配的**——
这与「HX5 的 U-Boot 会做完整 XG-PON bring-up、本板 U-Boot 只留 0x16644 = 0x0f02」完全一致。

## 7. 因此下一步（插纤前后都能做）

1. **给 0x17090000–0x170FFFFF 找时钟源**。候选：
   - TOPCRM（0x10e10000 区）里 PON 分支的第七条门控；
   - PON 窗口内 0x17040000 / 0x17050000 那两块（读 1，像门控寄存器组）；
   - 厂商 `zx_pon_clk_reset_init` 的 `top_crm+0x70 bit0/bit1`、`+0x60 bit9` 脉冲
     （debugfs 现在读不到，需要驱动内加一条只读通道）。
2. **插纤后第一件事**：`python pon_live_watch.py`（已备）看 `0x16105` 是否仍 = 0x10。
   若在「与 O5 活机逐位相同」的配置下 LOF 依旧，则本板的缺口 100% 在片内，
   与外部信号、OLT、光纤都无关——这条结论本身就是对用户承诺的正面回答。
3. 若 0x170B0000 块一旦能上时钟，`0x16105` bit4 应立即清、`0x16148` 出现
   `0x03FF0127` 形状的下行帧头、SDET FIFO 从 0 变成 `0x0804xxxx`。
